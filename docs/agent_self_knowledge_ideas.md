# What an agent should know about the model it runs on

## Context

The northstar's second thing to remember is that agents need to know about the model they are using, and should use that knowledge to adapt their methods to it. This notebook holds what that knowledge could be and where it could come from, and is indexed from [`in-flight_ideas.md`](in-flight_ideas.md). It keeps the substance of a question and answer first recorded on 2026-05-05, which asked what an agent benefits from knowing about its model beyond the size of its context window (llama.cpp's `n_ctx`), and how much of it llama.cpp's `llama-server` and Anthropic's API each expose. The statements about the two are as recorded then and have not been checked again. A server that would supply the Anthropic side is planned in [`mcp_servers_to_consider_ideas.md`](mcp_servers_to_consider_ideas.md).

The premise: most catastrophic failures of agents are not failures of reasoning but failures of self-knowledge, the agent not knowing some fact about itself.

## What an agent gains from each kind of knowledge, and where it comes from

| Knowledge | What the agent gains | From `llama-server` | From Anthropic's API |
|---|---|---|---|
| Capabilities: whether it can call tools, and in what style (native function calls, XML tags, JSON only); parallel calls; vision or audio; structured output (a JSON schema, a grammar) | it neither tries what silently fails nor refuses what it could do | `/props` gives `modalities` (the vision flag) and `chat_template_caps`; tool use depends on `--jinja` and the model's template, discoverable but not always cleanly | `GET /v1/models` and `GET /v1/models/{id}` give a `capabilities` object with `max_input_tokens` and `max_tokens`, documented for each model; tools, vision and extended thinking are described uniformly |
| The context budget now: the tokens in use, the headroom, whether context shifting or sliding-window attention is on (so whether an overflow truncates or slides), and the cost of a planned action ("will this 50 KB file fit?") | it neither overfills and is truncated mid-thought nor underfills and wastes the budget; the count of a planned action is the single most useful signal | `/props` gives `n_ctx`; `/slots` each slot's state; every completion's `timings` block (`cache_n`, `prompt_n`, `predicted_n`) lets the use be computed live, and a `truncated` flag shows an overflow | after the fact, the response's `usage` (input and output tokens, tokens written to and read from the cache); before, `/v1/messages/count_tokens`, which takes a request's shape; there is no session, so the caller sums the budget across turns |
| The knowledge cutoff and today's date | it decides for itself when to search rather than answer from memory, instead of stating stale versions, APIs or office-holders with confidence | no cutoff (one has to know which model was loaded); the date through the template variables `{{current_date}}`, `{{current_time}}` and `{{current_timestamp}}`, and `--chat-template-kwargs`; some models carry their cutoff in the system prompt | each model's reliable knowledge cutoff is published in the documentation, for the host to map from the model's id; the date is put in the system prompt |
| Identity and lineage: the model's name, version, parameter count and quantisation | a 4B model and a 70B model should decide differently when to delegate or attempt, when to ask or push through, and how far to trust their own reasoning; a small model that knows it is small can be more useful than a large one poorly calibrated | the `/v1/models` entry's `meta` (`n_vocab`, `n_ctx_train`, `n_embd`, `n_params`, `size`), and `/props` with `model_path`, `build_info` and the whole `chat_template`: the stack down to the quantisation | `/v1/models/{id}` gives the id, display name, type and snapshot date; no parameter count or quantisation |
| The reasoning configuration: whether thinking is on, its budget, and the form thoughts come back in | agents whose traces are stripped, or that expect a budget they do not have, behave erratically | `--reasoning-format` and `--reasoning-budget`, reflected in `/props`; responses carry `reasoning_content` | a `thinking: {type: "enabled", budget_tokens: N}` object in the request, and response blocks of type `thinking`, signed for verification; more structured than llama.cpp's, which is more flexible |
| The sampling parameters in effect: temperature, `top_p`, repetition penalties, mirostat | at temperature 0 an agent should commit to its first plan; at 0.9 it should expect variance and check itself more; it changes strategies such as "try N times and keep the best" | the whole `default_generation_settings` in `/props`, and overrides for each slot in `/slots` (temperature, `top_p`, `top_k`, mirostat, DRY, XTC and the rest) | the response does not echo them, so the caller knows only what it set: `temperature`, `top_p`, `top_k` and `stop_sequences` |
| The chat template's constraints: whether it takes system messages at all, tool messages and their shape, a prefilled assistant turn, several system messages merged or rejected | an agent that injects system instructions mid-conversation into a template that flattens them loses them silently | the Jinja source in `/props` (`chat_template`) and its parsed capabilities | abstracted away: messages go in Anthropic's schema and the templating is opaque, which for most users is a feature |
| The quirks of its tool-calling format: some models call tools reliably only with particular Jinja templates, or with `--jinja` and an override; some emit JSON in `<tool_call>` tags, others OpenAI's structured field; some support parallel calls in principle and degrade past two or three | it knows which family it belongs to | at the mercy of the model's training and template | one format across every Claude model: `tool_use` blocks from the model and `tool_result` blocks back, parallel use standardised |
| Speed and cost: tokens per second for processing the prompt and for generating, speculative decoding, reuse of the KV cache | it can weigh cost against latency ("five small calls or one large one?") | the `timings` block (`prompt_per_second`, `predicted_per_second`) and `/metrics` for Prometheus-style totals; no cost in money, being local | token counts in `usage` for the cost, `service_tier` in the response, and pricing documented for each model; no breakdown of each request's latency, which is measured by the clock |
| Concurrency and rate state: the slots, whether others are busy, whether the prompt cache will be reused (`cache_n`) | an agent running sub-tasks in parallel knows whether it gets parallelism or only a queue | `/slots`, the reference for a self-hosted server | the headers `anthropic-ratelimit-requests-remaining`, `-tokens-remaining`, `-input-tokens-remaining` and `-output-tokens-remaining`, and `retry-after` on a 429: accounting by quota rather than by slot, which tells an agent exactly when to back off |

## The three that matter most

If only three were kept: the live token budget, the capability and format of tool calling, and the knowledge cutoff with today's date. Those three prevent whole categories of failure; the rest is optimisation.

## The shape of the difference

The two expose different slices because they are different kinds of service: `llama-server` is a stateful local server that its operator owns, and Anthropic's API is stateless and shared. `llama-server` is more transparent about the model and its mechanics (the whole template, the whole sampling state, the state of the cache, the parameter count); Anthropic's API is more transparent about the model's contract (the capabilities object, the maximum input and output, the schema of tools and thinking, the budget of rate limits). For an agent, Anthropic's side serves planning ("can this model see images? how many tokens fit? how close am I to my quota?"), and `llama-server`'s serves diagnosis and tuning ("why did this overflow? which order of samplers is in effect? is my prompt cache being reused?").

Neither exposes the real-time occupancy of the context to the model itself: both leave the host to track it and to tell the model when it matters. Indeed, in most setups very little of this reaches the model at all; it stays with the host, not in the agent's prompt. The usual remedy is a short preamble that the host injects ("you are running on X with Y of context, today is Z, you have these tools"), crude but mostly effective.
